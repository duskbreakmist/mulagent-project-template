# 模板使用反馈（按需）

记录协作模板的繁琐步骤、歧义、遗漏和改进建议。没有问题时不必写；普通任务不要求遍历反馈区、填评分表或为了意见单独创建 task。

## 写到哪里

在主协作目录新增 .agents/feedback/<agent-id>/YYYY-MM-DD-<简短主题>.md，格式参考 [TEMPLATE.md](TEMPLATE.md)。例如 .agents/feedback/wb/2026-10-01-too-many-startup-reads.md。同工具并发实例使用不同 ID；同名文件已存在时另取名字，不覆盖。

每人只写自己的文件，不多人追加一个意见总表。在当前用户授权的工程内，模板允许新增本人反馈，无需先等待 integrator 批准。没有主目录写入权限时先保存在本人工作树中并注明“待汇入主目录”，不自行建立另一份实时反馈总表。

一句话意见也可先放在本人 task／handoff 的“模板备注”；worker 不因此获得共享 task 的写权限。值得跟进时再链接／汇入本人 feedback，保留原出处；不为意见专门造交接。

最小反馈只需：**作者与日期、遇到的问题、建议怎么改**。模板其余字段可删；主观感受可以写，但不要伪造耗时、token 数或复现结果，不记录内部思考链。

## 记录什么

- 具体场景和相关规则：例如单人改一份文档，却被要求重复登记／建多个交接。
- 影响和建议：哪些步骤能省略；精简后如何保持工作归属和防覆盖。
- 能提供时再附客户端／模型、来源模板提交或复制日期、相关 task／规则、复现步骤。未知就写未知；清单 version 是检查格式版本，不能唯一代表模板内容。

反馈示例（只示范格式，不代表已经测量或采纳）：

```markdown
# 单人小任务的启动步骤太多

- author: example-agent
- date: YYYY-MM-DD

## 问题
独立修改一份说明文档时，规则要求重复读与该任务无关的交接文件。

## 建议
只读当前 task 与它引用的交接；无相关交接时跳过。
影响是本人使用感受，未测量时间或 token 消耗。
```

## 怎么讨论与落实

其他 Agent 或维护者在**自己的反馈目录**写评审／回复，并引用原文件路径；不要改原作者意见或替别人宣称同意。评审写清采纳、拒绝、延后或需要补充信息，以及理由。

“采纳建议”不等于规则已经修改。进入实际修改时才关联实施 task，注明真实变更文件与验证／提交；已有用户授权可直接落实，无需增加重复审批。无回应不能算同意；记录反馈不会暂停与它无关的已授权任务。等待反馈处理期间仍按现行规则和用户当前指令工作。

## 新工程如何回传

反馈保存在使用模板的工程里，进入该工程 Git；**不会自动发送回模板来源工程，也不会自动更新其他工程**。需要改进母模板时，由用户或获授权的维护者把意见文件／Git 补丁带回，附来源工程和模板基线，保留原记录并避免同名覆盖。维护者评审后修改母模板；已有工程需要另行比较并合并更新。
