# 工程文档写作规范

适用于新增或修改的 README、技术说明、操作指南、API／CLI 参考及协作协议。任务、消息、交接和 CURRENT 继续使用各自格式，按本规范保持清楚、简洁和可核查；历史原文与归档快照保留当时语境。

## 采用的规范

| 层面 | 采用方式 | 一手参考 |
| --- | --- | --- |
| 写作风格 | Microsoft 为主要参考：用语明确、术语一致、步骤可执行 | [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/) |
| 开发者细节 | Google 补充接口、命令、代码示例和格式说明 | [Google Developer Documentation Style Guide](https://developers.google.com/style) |
| 内容结构 | 按 Diátaxis 区分教程、操作指南、参考与原理解释 | [Diátaxis](https://diataxis.fr/start-here/) |
| Markdown | 使用 GFM，并保持 CommonMark 基础语法兼容 | [GitHub Flavored Markdown](https://github.github.com/gfm/) |
| 约束强度 | 协作协议明确定义必须、禁止、建议、可选；英文规范词遵循 BCP 14 | [RFC 2119／8174](https://www.rfc-editor.org/info/bcp14/) |

用户当前要求和工程具体约定优先。Microsoft 是主要写作参考，Google 在未约定的开发者细节上补充；需要偏离参考时保持全文一致，影响重要约定的例外在相关 task／文档简要记录原因。外部写作指南不扩大任务权限，也不改变已有协调、验收或 Git 规则。

默认中文。采用清晰、简洁和一致的原则；英文大小写、冠词、拼写与标点规则按中文语境调整。代码、字段名、状态枚举、命令、API 和产品名保留实际拼写，不为符合文风改变机器可读标识。

## 内容组织

| 类型 | 回答的问题 | 写作重点 |
| --- | --- | --- |
| 教程 | 初学者怎样完成一次练习？ | 固定起点、连贯步骤、预期结果和成功检查 |
| 操作指南 | 怎样完成某个实际目标？ | 前提、推荐路径、操作、验证和必要故障处理 |
| 参考 | 参数、接口或规则准确是什么？ | 完整、一致、可查；说明默认值、边界与错误 |
| 原理解释 | 为什么这样设计？ | 背景、关系、取舍和适用范围 |

先确定读者和本页目标。README 作为入口提供用途、快速开始与导航；详细参数和设计原因链接到对应内容。小文档可以用分节区分不同类型，不要求每页新建四份文件。协作记录保留任务格式，不为套用分类增加重复表格。

## 写作与示例

- 先给读者需要的结论或动作，再补充理由。用短句和主动表达，明确谁执行、作用于哪个对象。
- 第一次出现重要术语时解释，之后使用同一名称。描述性链接应告诉读者目标是什么。
- 面向新工程的分发说明不引用读者无法获知的历史（已移除的依赖、旧版流程、未定义的来源工程）；描述当前行为。可操作的否定保留，考古性的否定删除。
- 按顺序执行的操作用编号列表；条件、权限、依赖和执行目录放在相关步骤之前。每步聚焦一个明确动作。
- 命令与代码放在标明语言的围栏中；参数、字段、文件名等代码元素用行内代码。区分实际可运行值与需替换的占位符。
- 示例说明前提、输入和预期输出；路径应适合目标环境。通用说明使用相对路径或清楚标注的示例位置，避免把某台机器的路径写成普遍要求。
- 区分事实、推断、建议和未验证项。实测结果附可复现命令与必要版本／环境；引用外部结论给出直接来源，不把旧记录当成新验证。

## Markdown 排版

- 标题按层级组织，标题后留空行；列表与相邻段落间留空行，避免不必要的嵌套。
- 比较、映射和参数表使用表格；连续操作用编号步骤；独立事项用项目列表。
- 文件树放在 text 围栏中，在行尾标注职责；说明折叠范围，区分源码、默认分发、可选组件和运行产物。
- 图片有替代文字；图示说明对象和关系。链接到真实文件／页面，定期核对相关本地链接。
- 使用 GFM 支持的语法；只有目标渲染器明确支持时才使用额外扩展。

## 协作协议的约束词

下列中文词义由本工程明确定义；英文关键词仅在全大写并作为规范要求使用时采用 RFC 2119／8174 的含义：

| 中文词 | 英文规范词 | 本工程含义 |
| --- | --- | --- |
| 必须 | MUST | 属于绝对要求；执行者需要满足 |
| 禁止／不得 | MUST NOT | 属于绝对禁止 |
| 建议 | SHOULD | 原则上遵循；有充分理由时可例外，需理解影响 |
| 不建议 | SHOULD NOT | 原则上避免；例外需有理由并理解影响 |
| 可选／可以 | MAY | 执行或不执行均允许 |

规则应写清执行者、触发条件、行为和可验证结果，避免用“尽量处理”“适当协调”代替操作边界。涉及所有权、接受任务和停写确认时保留协议中明确的真实证据要求；不能把建议或例子自动升级为必须。

## 交付前检查

1. 读者能否找到目标、适用范围和前置条件？
2. 步骤、参数与示例是否和实际实现一致，命令是否在可行范围内验证？
3. 术语、机器标识和约束强度是否一致，事实与未验证项是否分清？
4. 新增或修改的链接、表格、围栏与文件树是否可读且目标存在？
5. 是否保留既有作者内容和历史语境，删除了无关重复内容？

现有模板检查器只覆盖组成文件、编码、本地链接和任务状态等项目；通过检查不等于自动认证所有外部写作指南，也不替代内容审阅。新增模板组成文件须同步维护 manifest；普通文档内容修改无需改变清单格式版本。
