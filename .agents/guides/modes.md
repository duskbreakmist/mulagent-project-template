# 协作模式与独立对照（按需阅读）

## 1. 模式不是进度状态

status（todo / in_progress / review / done 等）描述进度；collaboration_mode 描述本任务如何开展。并行还是串行是执行安排，也不等于任务拆分方式。

| collaboration_mode | 用户选项 | 含义 |
| --- | --- | --- |
| serial | 单人串行／串行接力 | 一人依次完成，或逐阶段按真实交接继续 |
| collaborative | 分工协作 | 拆分不同职责／模块，分别完成后整合 |
| independent_compare | 独立对照 | 各 Agent 独立完成同一份目标，提交后再比较 |
| unset | 尚未选择 | 尚无模式决定，不启动依赖该决定的工作 |

一个项目可混合模式，按具体 task 决定。独立对照是同一任务的多个候选产出，不必为了登记每个 AI 而拆成不同目标的子任务。

## 2. 提问触发规则

1. 优先本轮明确指令，其次当前 task／明确继承的父任务，再检查 coordination.md 的 default_collaboration_mode 与 default_mode_source。已由用户明确设定的有效工程默认可用，task 记 mode_source: project_default 并注明实际来源；不重复提问。明确交给当前实例的单人任务可记录 serial + 用户任务来源，但不能据此设全工程默认。
2. 没有上述有效来源或出现冲突时，只有本任务 integrator 向用户提问；先把 mode_question_status 记为 pending。worker 看到待问／待答时不再次提问，也不替用户选择。
3. 有交互提问工具时使用实际工具，显示下面三个选项；无工具时发同样的文字问题。是否显示弹窗／选择卡取决于客户端，AGENTS 文本不能强制 UI。
4. 推荐项按任务语境标注；客户端预选项、超时、无回复或另一 Agent 的猜测都不算用户选择。
5. 将真实回答写入 task 的 collaboration_mode、mode_source 和“Mode Decision”，mode_question_status 改为 answered。已有明确模式时用 not_needed；同任务后续轮次直接读取，只有用户切换模式或出现明确冲突才重新询问。
6. 等待时可只读资料、检查环境、整理与模式无关的工作；不派发外部任务、不改共享实现、不先开始相互依赖或独立评测的正式产出。用户已授权的模板维护等无关工作可以继续。

建议问题：

> 当前任务希望采用哪种协作模式？
> ① 串行接力：阶段完成后交给下一位。
> ② 分工协作：不同子任务分别完成后整合。
> ③ 独立对照：不同 Agent 各自完整完成同一任务，最后比较。
> 若已有明确选择，本任务不重复询问。

工程默认初始 unset。历史多数任务是 serial 不构成用户设定默认的证据；用户明确改变要求时覆盖默认。默认没有额外授权派发其他应用／子 Agent。

模式选择不等于授权启动其他应用／子 Agent；实际派发仍需用户授权与可用通道。

## 3. 独立对照的产出目录

任务仍只有一个 owner 负责目标与统筹，participants 可以有多个；每个参与者只写自己的候选与 RUN.md，由 integrator 更新共享任务表。不要让两个 AI 同时改一个 report.md。

默认目录（只是示例，不预先登记或启动这些 Agent）：

```text
results/<TASK-ID>/<RUN-ID>/
  input.md                 # owner 固定的公共输入、基线和评价条件
  gpt/
    RUN.md                 # 本人状态、版本、工具、预算、限制、验证和结论路径
    report.md              # 或自己的实验／实现
  wb/
    RUN.md
    report.md
  comparison/
    review.md              # 收齐／截止后，由指定评审者填写
```

RUN-ID 如 run-001，用于区分同一任务的多轮比较。每轮 input、参与者、预算、时间条件、验收和比较标准先固定；模型／工具版本不能确认时写 unknown，不根据品牌名推断。禁止在比较条件中保存 API 密钥等凭据。

任务字段 output_root 指向本轮目录；可根据已有项目明确改成其他结构，但必须含任务／轮次和各 Agent 自己的范围。原有作者目录与报告保留，不批量迁移。

[results/README](../../results/README.md) 说明正式产出管理；[RUN 模板](../runs/TEMPLATE.md) 供需要时复制。正式比较结果进入 Git，不放默认被忽略的 scratch。

## 4. 保持独立，之后再对比

- 提交前可读固定 input、规则、自己的资料／状态和必要的协调消息；不读其他候选的报告、代码、核心结论或带这些内容的中途评审。共享 task／CURRENT 不提前披露候选核心答案。
- 截止或共同约定的提交阶段后，汇总已经交付的候选，再由指定 reviewer 按事先约定标准评估；某参与者未交付则明确记缺失，不能将其伪造为完成。
- 修改候选或看到其他答案后再改结果，要另记修订版本／新轮次和暴露情况，不把受影响的结果称为独立首稿。
- 比较正确性、证据、覆盖、可复现性、测试、成本与延迟等实际指标；不把篇幅、相互赞同或多数票直接等同于正确。
- 原始结果保留，比较结论写 comparison，由用户／integrator 决定采用或组合哪些方案。切换成协作整合时记录新的任务阶段或任务，不直接覆盖候选原文。
- 提示词只形成行为约定，不提供真正的盲测或权限隔离；需要更强隔离时使用不同工作树／访问权限，避免当前会话已看过对方答案。不得宣称历史研究已经严格独立。

## 5. 独立代码候选

研究文档可在同 checkout 各写自己的子目录，由一人串行提交。独立实现要各用 worktree + 分支，基于同一指定提交，保持常规 src/ 结构和可复现构建；不能为了分目录破坏工程布局。

主目录对应 Agent 子目录记录提交、复现方法、测量和报告，实际代码留在各自工作树／分支。仅有不同分支名但仍在同一个 checkout，依然不能隔离编辑。
