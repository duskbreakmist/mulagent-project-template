# 对单文件多 Agent 协作方案的评估

日期：2026-09-30。性质：对用户提供的对话与本工程实际状态的评估；不是 WorkBuddy 的回复。

> 更新：后续用户要求拆分模板。当前可复制版本见 [project_templateA 使用说明](../project_templateA/template_readme.md)；下文的单文件初始化描述保留为初始版本评估。

## 判断

方向合理：把稳定规则、任务事实、作者产出和 Git 隔离分开，足以支撑个人工程中的跨工具协作。“自展开的 AGENTS”也可实现，但它依靠 Agent 实际读取并执行，不是文件本身拥有魔法。

这里需要的是轻量的共享黑板和明确的整合职责。不能只靠角色名字、提交标签或一份接龙表解决并发。

## 逐项修正

| 对话中的观点 | 评价与采用方式 |
| --- | --- |
| AGENTS 是通用入口 | 合理；是否自动读取由具体工具决定。已有支持生态不等于所有 AI 都支持；WorkBuddy 尚未实测。 |
| 进度按任务，能力按 Agent | 采用。任务文件是主入口；保留 gpt/、wb/ 的历史研究产出，CURRENT 只是摘要。 |
| 一任务一 owner，上下级拆任务 | 采用。角色按具体任务确定，不根据厂商固化“谁更聪明”；新增分工必须真的被接收。 |
| 分支／worktree 隔离办公桌 | 使用 worktree 才隔离工作文件和索引；同一个 checkout 创建两个分支不够。小规模分文件写文档可以串行整合，无须一律禁止共享 checkout。 |
| 所有 worktree 的 tasks 构成共享黑板 | 原方案漏了这一步。它们是各分支快照，不能自动看到未提交进度。指定主协作目录，worker 读主目录、写自己的交接，integrator 串行改任务表。 |
| 检查 marker 就能避免重复初始化 | 不够。marker 只说明某次结构初始化完成；必须检查所需文件和版本。标记不能取代登记或防并发锁。 |
| “不存在就创建”基本能避免同时启动冲突 | 普通 exists→write 有竞态。初始化器使用独占锁、完整写临时文件、硬链接独占发布，目标存在时保留；标记最后发布。 |
| Agent 都在 agents_list 末尾接龙 | 单人可行，并发仍会覆盖。采用单 integrator 串行维护，其他实例通过自己文件提出登记请求。 |
| Agent 不准改他人的 scope | 是约定，不是安全隔离。需检查 scope、接口与依赖，真正隔离靠 checkout／文件权限和 review。 |
| Git author／Task 标签是真实身份 | 只能辅助追踪，全部可自报和修改。密码学签名另有密钥与验证。普通 worktree 默认还共享配置，反复 git config user.name 会互相影响。 |
| Git commit 是不可变工作日志 | 提交对象有内容寻址，但引用可移动、历史可改写；不能称整个日志绝对不可篡改。 |
| Git／代码永远高于任务、计划和聊天 | 不采用固定排序。用户当前指令决定授权；代码说明实际行为；任务说明当前分工；计划说明意图。冲突需对照版本、证据和用户要求。 |
| Orchestrator 可以自动给 WB／DS 派工 | 只有实际通信渠道和授权才能派发。写一个 task 不会唤醒外部应用；本次没有伪造对方收到任务。 |
| A2A 可以以后接入 | 可行但不是当前必要条件。先形成可审查文件交接；之后再实现发现、认证、任务生命周期、超时与结果回传。 |
| “解决 80%～90% 打架” | 未提供测量依据，删去这个量化承诺。衡量重复编辑、冲突、接手时间与状态一致性才有意义。 |

AGENTS.md 是面向 coding agents 的开放文本格式及工具生态入口；具体客户端负责解释、加载和执行。[AGENTS.md 官方说明](https://agents.md/)

Git 官方说明 worktree 的独立工作区及共享／独立引用、配置规则；本工程同时用临时仓库测试“配置可共享，工作文件不实时同步”。[Git worktree 文档](https://git-scm.com/docs/git-worktree)

A2A 定义 Agent Card、任务、消息与交付物等跨 Agent 交互概念；本次只借鉴任务／交付结构，并未实现 A2A 服务。[A2A 核心概念](https://a2a-protocol.org/latest/topics/key-concepts/)

## 本工程落地

- 根 AGENTS 保持入口与稳定约定；通用可复制版本放 gpt/templates/AGENTS.md，包含初始化代码。
- agents_list 分 confirmed（本人确认）与 observed（从产出观察），不冒充他人注册；不登记未实际参与的 DeepSeek。
- .agents/tasks/COLLAB001 对应本次改造；R001 对应 GPT 研究交付；R002 导入 WorkBuddy 的待核实清单；R000 只是后续综合方案提议。
- 主目录配置为本机原始 main 工作树，所有 worker 从它读取当前任务。这个绝对路径只进本地 Git 配置。
- 工作记录保留本工程已有 docs/CURRENT.md、gpt/CURRENT.md，不再另建一套 docs/codex 进度。
- 两份既有研究正文保留原样。现在不创建无人使用的 WB／DS 工作树或背景调度器；真正启动并行实现时按任务开工作树。
- 为“GPT 看 WB 遗留什么”提供 R002：原报告 §13 的七类引用／主张待核实，§14 的原型建议未实现。只导入这些可观察事实。
- docs/collaboration 保留人类操作入口，实际规则在 .agents/PROTOCOL.md；旧 topics 路径不删除，历史消息保留，未来统一用 task ID。

## 最小协作例子

GPT 定义管线时先提交契约和验收，建立 proposed 子任务，分别写给 WB 与 DS 的请求；用户或真实通信桥让对方读取。对方确认后整合者更新 accepted、scope、基线和分支。

WB／DS 各自在自己的工作树实现，在主协作目录的自己消息／交接文件报告结果；不直接改 main。GPT 根据真实产出审查、整合，并对整体运行结果验收。改变架构必须提出证据和影响范围；无人回复则维持提议状态。

## 适用边界与验证

初始化锁只保护初始化，不是源码编辑锁、任务分配事务或权限防火墙。主目录状态写入依赖 integrator 串行操作；跨机器或多个并发协调者需要真正的状态服务、事务／CAS 与权限管理。

初始化器依赖 Python 3.9+ 和支持硬链接的文件系统。本机已验证；网络文件系统不保证可用，失败时保留文件并要求人工检查。残留锁不得按时间自动清除。

尚未验证 WorkBuddy 的自动规则加载、双方实际收发、远程 clone 状态同步、自动唤醒或密码学签名。这些不能因写完协议就宣布成功。
