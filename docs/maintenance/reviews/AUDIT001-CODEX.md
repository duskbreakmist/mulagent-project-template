# 当前模板的需求与可维护性评估

本报告对应 [AUDIT001-CODEX](../tasks/AUDIT001-CODEX.md)，审查起点为 `2a318a1`。用户选择单人串行；内部只读调查提供线索，修复由同一 owner 实施。检查活动源码、协议、分发清单、安装升级、可选工具、测试与维护入口；旧归档仅用于理解已有验收范围。

## 结论

模板适合**有人监督的工程协作**：能够给单人开发、跨工具串行接力、worktree 分工和同题独立调研提供一致的任务、所有权、交付与 Git 规则。安装升级已经具备基线追踪、定制保护、冲突候选和回滚机制。本轮发现的边界缺陷说明，原有 94 项测试通过不足以保证这些机制的所有状态转换正确。

可选工作台已具备可运行的本地协调核心；真实客户端的启动、额度识别、退出后停写证明和跨机器状态同步仍未完成验收。因此，作为协议与本地辅助工具基本满足当前定位；如果验收目标是多个实际 AI 客户端无人值守自动接力，目前只能判断为部分满足。

可维护性总体可控：默认分发仅 34 项，Python 工具使用标准库，源码、业务种子、测试和历史有明确分层。主要负担来自重复边界规则、工作台单文件集中、手工维护多个记录入口以及缺少最低版本回归。本轮优先修复正确性并增加防回归措施，保留现有 CLI 和分发结构。

## 可维护性判断

### 结构与依赖

母仓库与业务安装分离是合理设计。管理器只取 Git 普通文件对象，安装清单限定通用协议；母仓库 README、测试、维护历史和可选服务不进入默认业务包。继续保持这个边界，避免业务工程为了消费协议承受整套开发历史。

审查起点的管理器约 538 行、检查器 178 行、工作台 915 行、relay 264 行。工作台把数据库状态机、迁移、进程监督、HTTP 和内嵌网页集中在一个文件，后续真实适配器增加时会显著扩大修改面。当前尚未引入新的第三方依赖，模块规模也未妨碍针对性测试，因此本轮不做全面拆分。

建议在接入第一个真实适配器时，按“状态服务、适配器监督、HTTP/UI”拆分工作台，并用现有 CLI 场景回归保持兼容。该拆分应由实际接口变化驱动，不能仅按行数机械切文件。

### 规则与重复

manager 和 checker 独立执行具有明确价值：下载内容不能成为验证它自己的可执行依赖。两处路径、运行记录与核心清单规则仍存在维护重复，本轮通过交叉用例约束，而没有新增运行时公共模块及分发兼容负担。

空种子检查使用独立维护基准，而不是猜测“正文是否像某个真实人名”。它能阻止任意未审查文本混入种子，但合法文字修改也需要同步基准。维护者必须先确认没有实际状态，再更新哈希；基准是防误改措施，不是对恶意维护者的安全认证。

### 状态与恢复

正式 task 的授权、scope 和验收由 Markdown 保存；工作台的 owner、epoch 和占用范围由数据库管理。这两个层面以前缺乏明确操作说明，本轮补充了建任务、里程碑核对与交接规则。当前没有自动同步；快照不能反向变成可写任务板，数据库丢失也不能证明写者已停止。

CURRENT 应只做恢复导航。历史事实继续保留原日期、验证环境和未验证项，避免把某次绿色 CI 继承成当前代码已通过。维护 task 是本轮详细记录入口，不把临时子任务写成多个工程登记或重复任务板。

### 测试与版本

此前 94 项基线回归通过，但缺少跨平台别名、多个并发测试、未知生命周期成功退出和候选接力后的消息限制等组合场景。这些都应作为长期回归，而不是用扩大静态规则文案代替测试。

CI 增加最低 Python 3.9 与 3.13 的双版本矩阵，覆盖 Windows 和 Ubuntu。用户追加推送授权后，首轮发现Windows 3.9相对源测试只模拟 `os.getcwd` 的跨版本问题；改为指定真实 `cwd` 的CLI子进程后，四组合全部通过。未通过跳过测试或修改产品逻辑消除失败，详见下节。既有标签保持原样，本轮推送main，不发布新版本标签。
