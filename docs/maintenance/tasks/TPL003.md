## 模板备注与建议（尚未实施）

1. **优先补维护层检查和分发边界回归。** tools/check_template.py 的链接校验仅覆盖 manifest 中的 Markdown，任务状态仅扫描 .agents/tasks；docs/maintenance/tasks 的状态和维护链接未纳入。安装器 protected 的运行目录列表未包含 docs/maintenance、tests、.github，不能单靠它拦截维护文件误入清单。建议增加母仓库专用检查／测试，避免扩大业务安装清单。验收：错误维护状态、维护断链、维护文件混入清单或种子污染能使母仓库验证失败；业务工程真实状态仍允许保留。
2. **明确多人维护时的状态入口。** 当前维护身份和 scope 记在 task 足够支持单人；多人参与时仍需明确实际维护整合者、活跃任务查找方式和共享写入范围。维护 README 的“先查看 TPL002”属于固定历史入口，任务增长后容易过时。建议从维护 CURRENT 链接当前任务，复杂协作再增加维护侧索引／协调记录，根种子继续空白。验收：新会话能直接找到活跃任务、负责人和 scope，完成任务不被写入分发状态。
3. **用少量完整场景检验协议。** 增加人工场景验收说明，覆盖单人完成、跨客户端接力、双 worktree 分工、首稿隔离的独立对照、原执行者失联恢复；每个场景固定输入、期望状态、产出与失败判定。验收关注 scope 是否重叠、接受是否有实际确认、结果是否可追溯、共享状态是否只有一个事实源。现有 Python 测试不能证明真实客户端遵守这些文字约定。
4. **保持入口轻量并消除维护文案歧义。** template_readme 开头“可直接复制”需结合后文按清单复制理解；维护 README 的“本轮改动已在本地提交”等阶段陈述宜归入 task／CURRENT，稳定入口只保留操作流程。建议用“开发母仓库／安装到业务工程／升级业务工程”的简短导航区分场景；普通任务继续按需读取，不增加例行登记表或评分表。验收：入口能选对操作，安装范围与实际工具一致。
5. **协议先稳定，自动调度单独演进。** 可选 relay 已明确收件 ack 不代表接受任务，且不自动启动客户端。真实四客户端收发、失联恢复与人工停止确认应先验收；额度查询、自动唤醒和轮换另开授权明确的开发任务。验收分别记录协议／队列测试、客户端实测和发布版本，不把历史测试通过推定为当前互通。
