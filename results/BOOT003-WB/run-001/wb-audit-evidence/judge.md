## 二、判断要点逐条回答

### 要点 1：历史上真实发生过哪些"模板自己驱动多 AI 维护模板"的实例？

【事实】严格意义上：**0 次**。没有任何一次多 AI 参与是由模板自身的协议机制或工具触发的。

【事实】但真实发生过 **1 轮多 AI 同题协作**（2026-10-11 结构定位审计）：
- 实例数：**4 个**（codex-structure、wb-structure、zcode-structure、wb-hy4）。TPL003 记录用户说明"在 Codex、WB、DSH、ZCode 四个客户端启动了五个 Agent"，但第五位身份"不能确认"，且 DSH 无任何落盘产出。
- AI 种类（按 commit message 前缀统计）：**gpt、codex-*、zcode-*、wb-*** 四族；实际同轮并发跨 **3 族客户端**（Codex / WorkBuddy / ZCode）。
- 是否真的并行：**是"同时在线"，不是"机制化并行"**。TPL006 观察到 TPL003 未提交文件与运行中测试进程、TPL005 观察到 TPL004 提交与共享 CURRENT 幻影 —— 证明多会话确实同时存活；但同一 checkout 上的 Git 操作靠时间错开侥幸串行，RUN 记录明写"不是机制保证"。
- 谁汇总：**用户于 2026-10-11 16:02 口头授权 wb-hy4-20261011 收尾**（RUN 记录首行与收尾节、提交 8d2645f）。模板未产生汇总者。

【事实】此外 7 个任务（DOC001–004、PUB001、ORCH001、TPL001/002）全部是**单实例串行**，由用户逐个指派，不存在 AI 之间的互相驱动。

### 要点 2：每一环是"自动"还是"人工搬运"？

| 环节 | 判定 | 依据 |
| --- | --- | --- |
| 拉起其他 AI | **人工** | relay 文档明写"消息工具不自动启动任何模型""人工把接手提示词粘贴到目标客户端"；TPL003 记录系用户手动在四个客户端启动 |
| 下达同源指令 | **人工** | RUN 记录"提示词（四实例同源）"由用户分发；无任何自动广播通道痕迹 |
| 任务 ID 分配 | **人工／失控** | 各实例自选编号，四实例均"兼任 task integrator"，共享 integrator  vacant |
| 模式声明 | **各自人工判断** | 无 RUN 记录在前即自称 independent_compare；盲态三档不一致 |
| 结果落盘位置 | **违反协议，人工习惯** | 写进 `docs/maintenance/tasks/`，而非 `results/<TASK>/<RUN>/<agent>/`；`results/` 至今只有 README.md |
| 汇总与合并 | **人工指定** | 用户 16:02 授权；RUN 收尾节明写"由用户在对话中逐项授权" |
| 代中断者收尾 | **人工** | zcode 的 TPL005 由 wb-hy4 手动 `git commit` 代提 |
| 推送 | **人工** | PUB001"GitHub 推送按惯例由用户执行" |

结论：**整条链路每一环都是人工搬运**。协议与工具在其中只起到"产出格式约束"作用（各 AI 自觉写出 status/owner/scope/base_commit/Verification/Remaining 字段），不起到"驱动"作用。

### 要点 3：中断／代收尾说明自举链条哪里不可靠

【事实】失效点依次是：
1. **无会话存活/心跳机制** —— zcode 断了 15 小时无人察觉，靠汇总者做 `git status` 才发现 staged 文件。
2. **无 handoff 强制** —— 协议要求中断时写 handoff，实际留下的是未提交/暂存文件。
3. **共享文件无锁** —— CURRENT 幻影 M 是并发写已发生的实证。
4. **无 integrator** —— 无人有权自动接管孤儿任务，只能等用户授权。
5. **Git 通道与环境不可靠** —— 推送被重置、沙箱阻断测试、短路径 CI 失败。

【推断】这套模板目前对"某个参与者掉线"是**零自动容错**：恢复动作 100% 由人完成。

### 要点 4：agent_workbench / agent_relay 有没有真实驱动过客户端？

【事实】**没有**。三条独立证据：
1. `tools/agent_workbench.py` 的 `demo()` 注册的 agent 全部带"（演示）"后缀（`tools/agent_workbench.py:839-842`），且明确"不会调用模型，不会伪造真实客户端已经上线"（`docs/optional/agent-workbench.md:60`）。
2. 工作台唯一被记录的真实调用是 DOC001 对新工程跑 `status`，**返回空登记/空任务/空轮次**（`DOC001-CODEX.md:32`）—— 即从未有任何真实 Agent 通过工作台 join/claim。
3. relay 的运行队列目录 `.agent-relay/` 在本机不存在；文档自述其工作方式是"复制接手提示词 → 人粘贴到目标客户端"，且"MCP 支持收发工具调用，不足以证明客户端会被外部消息自动唤醒"（`docs/optional/agent-relay.md:47`）。

【事实】工作台自身的质量是扎实的：70 项完整回归 + 18 项场景测试通过、真实浏览器演示、Windows UTF-8 问题已修。但验收边界被 ORCH001 自己写死为"**不宣称四个实际客户端已经自动接入**""模拟成功不能推定为实机互通"。

【未验证】真实客户端的额度信号、外部启动、退出后无残留写者 —— 三项均为 ORCH001 Remaining 明示的未做项。

### 要点 5：自举成熟度分档

先给档位定义（本评审自定义，供横向对齐）：

| 档 | 定义 |
| --- | --- |
| L0 | 无多 AI 参与痕迹 |
| L1 | 多 AI 真实产出，但**启动、指派、汇总、收尾全人工**；协议仅被"读懂并照格式写" |
| L2 | 模板工具（登记/认领/模式协商/状态同步）被**真实 AI 实际调用**，至少支撑过一轮完整任务 |
| L3 | 工具能**自动启动／唤醒／接力**真实客户端（额度退出→备用接手闭环） |
| L4 | 模板可**自行发起、分派、验收并合并**对自身的维护，人只做审批 |

**判定：部分能 —— L1（上限未达 L2）。**

理由（全部对应上文事实）：
- **够 L1**：4 个不同 AI 在 3 个客户端里，按协议产出格式完成了同题审计并全部落盘成提交（01f66e7 / 7387004 / 4f71580 / 71ede66），产出间可互相印证、结论收敛点一致（RUN"三实例一致，可采信"4 条）。协议**作为文本规范是有效的**。
- **不够 L2**：协议要求的核心机制（RUN 记录前置、integrator 分配任务 ID、`results/<TASK>/<RUN>/<agent>/` 隔离、盲态一致）在唯一一次多 AI 实战中**全部被绕过**；工作台/relay 这两个自动化组件零真实调用。
- **不够 L3**：无客户端启动、额度感知、自动接力的任何实证，ORCH001 明示未做。
- **不够 L4**：任务发起者始终是人，汇总者是人指定的，推送是人做的。

### 【推断】

1. 当前"多 AI 协作"本质是**人肉编排 + 协议约束的文档格式**，模板提供的是"共同语言"而非"调度器"。
2. 若移除用户这一环（不再手动启动客户端、粘贴提示词、指定汇总者、点击推送），本仓库的多 AI 协作**会立即退化为 0**——没有任何组件能替代。
3. ORCH001 工作台已具备达到 L2 所需的机制（登记、认领、scope 冲突、epoch 失效、接力、人工界面），缺的不是代码而是**一次真实接入的验收**；瓶颈在客户端侧能力（外部启动、额度信号），不完全在模板侧。
4. 协议文本与实战行为的偏差（任务号抢占、盲态不一致）说明：**协议被读懂但未被强制执行**，缺少可执行校验（TPL003/005/006 三实例共识的"维护边界回归测试"至今未实施，列在 RUN 未实施候选第 1）。

### 【未验证】

1. 真实四客户端额度/启动适配（ORCH001 Remaining、PUB001 Remaining 均明示未做）。
2. 跨 harness 真实任务试点（TPL006 建议 3，未实施）。
3. 独立测试 Agent 对工作台原型的审查（ORCH001 自述"自动测试由本会话编写并运行，不算独立审查"）。
